# File-by-file, strict off vs Strict immediately: what 5 frontier AI models actually said

**The question:** You are inheriting a 60k-line JavaScript codebase and adding TypeScript. Turn on `strict` immediately and suppress the errors, or migrate file-by-file with strict off?

We asked 5 frontier models this exact question, at the same time, with the same instructions, and made each one commit to a single answer instead of hedging. Here is how they split.

## The scoreboard

| Pick | Models | Count |
| --- | --- | --- |
| **File-by-file, strict off** | Claude Opus, Llama 4 Maverick, DeepSeek V3.1 | 3 |
| **Strict immediately** | GPT-5.6 Sol, Gemini 3.1 Pro | 2 |

## Every answer, unedited

### Claude Opus <span>Anthropic</span>

**Picked: File-by-file, strict off**

> Turning on `strict` across 60k lines at once buries you in thousands of suppressed errors that become invisible tech debt and get ignored. Migrating file-by-file with `strict` enabled per-file (via `// @ts-check` or incremental includes) gives you real, enforced type safety on the code you've actually converted.

### GPT-5.6 Sol <span>OpenAI</span>

**Picked: Strict immediately**

> It establishes a clear safety baseline and prevents new non-strict code. Track suppressions explicitly and remove them incrementally during migration.

### Gemini 3.1 Pro <span>Google</span>

**Picked: Strict immediately**

> Turning on `strict` immediately stops the bleeding by ensuring all new code is fully type-safe from day one. Suppressing existing errors creates a clear, trackable burndown list of technical debt rather than allowing loose typing to proliferate indefinitely.

### Llama 4 Maverick <span>Meta</span>

**Picked: File-by-file, strict off**

> Turning on `strict` immediately would result in a huge number of errors that would be overwhelming to address all at once, and suppressing them would not provide the benefits of TypeScript. Migrating file-by-file with `strict` off allows for a more incremental and manageable transition.

### DeepSeek V3.1 <span>DeepSeek</span>

**Picked: File-by-file, strict off**

> A gradual migration reduces immediate disruption and allows for incremental type safety improvements. Turning on strict immediately would overwhelm with errors and hinder development progress.

## The verdict

Claude Opus served the user best by advocating for a file-by-file migration with strict off, emphasizing the importance of addressing tech debt incrementally while maintaining type safety on converted code. In contrast, both GPT-5.6 Sol and Gemini 3.1 Pro suggested turning on strict immediately, which could lead to overwhelming errors and hinder the migration process.

## Why this is worth two minutes

Neither answer here is wrong. That is exactly the problem with asking one model: you get a confident, well-written answer with no indication that another equally capable model would have told you the opposite. The disagreement is information, and a single-model workflow throws it away by construction.
